PokéPulse · predictor guide

What the meter knows.
What it hasn’t solved.

A guide to the actual battle-search algorithm, how it receives your game state, and why the current percentage can still be misleading.

Source audit: October 6, 2026 · Current source and packaged runtime files matched when checked · Self-contained, offline HTML

The current meter is not a calibrated full-battle win probability.

It searches a simplified duel between the two active Pokémon, against an adversarial move-selection model. It produces a lower and upper bound on that model’s outcome. The single displayed percentage can be the lower bound or a retained earlier estimate. Treating its complement as your chance of losing is often wrong.

The previous reuse change passed controlled tests, but your live behavior remains unresolved. Those tests did not establish that real attacks would stop producing large shifts.

01 / Objective

Search for a winning policy, not a promising hit.

The intended question is: “From this state, how likely is victory if I choose a good move now and keep choosing good moves as events unfold?” The engine must carry consequences forward: HP, status, PP, stat stages, wake-up, the next move, and eventually the outcome. Immediate damage or a large HP lead cannot answer that question by itself.

The current implementation asks a narrower question: “Can the player win this active one-on-one matchup, under supported mechanics, if both sides choose strategically?” An opposing faint is counted as a win immediately, even if the trainer has other Pokémon. Your own faint is counted as a loss immediately, even if your remaining team would easily win.

1. Read RAMObserve the active battlers.
2. Build a stateHP, moves, status, counters, PP.
3. Expand turnsMove pairs and random outcomes.
4. Back up valuesCombine probabilities and decisions.
5. RenderPublish bounds, select a display value.

Randomness has probabilities.

Damage rolls, misses, paralysis, thawing and speed ties create chance branches. Their probabilities multiply along a path. Equivalent resulting states can be combined.

Move choices need an opponent model.

The engine does not choose enemy moves uniformly at random. It lets the opponent use a strategy that minimizes your outcome. That can be more pessimistic than the ROM’s actual AI.

The mathematical objective
V(state) = max over your move distribution p min over enemy move distribution q Σ(move a, move b) p(a) × q(b) × Σ(outcome s′) P(s′ | state, a, b) × V(s′)

Each move pair is one cell in a payoff matrix. The cell contains the probability-weighted values of its possible next states. Both players commit to their move before random outcomes are seen. Allowing mixed strategies avoids pretending you know the opponent’s selected move.

A terminal modeled win has value 1; a modeled loss has value 0; simultaneous fainting is assigned 0.5. Unknown continuations have an interval [0, 1], not an HP-based guess.

For example, the illustrative matrix [[0.9, 0.4], [0.3, 0.8]] has a mixed-strategy value of 0.6: you mix the two rows equally; the enemy mixes the first column with probability 0.4. These are invented payoffs explaining the decision rule, not measured Pokémon outcomes.

02 / Expansion

What happens inside one simulated turn?

1

List legal, supported moves for both sides.

Remove exhausted PP and currently blocked moves. Supported status moves remain available. Unsupported status moves are omitted and reported. There is no switching, bag-item action, or full-party planning.

2

Evaluate each pair of selected moves.

Priority comes first, then effective speed and Trick Room. Equal speed produces two equally weighted order branches. Both moves were selected before the order and outcomes are observed.

3

Execute the first action as probability branches.

Sleep counters advance; waking can allow an action. Freeze, paralysis and confusion can prevent or change it. A usable action consumes PP. Accuracy then splits hit and miss paths, and damage rolls split resulting HP. Supported setup, recovery and status moves update the state.

4

Execute the second action on each resulting state.

Recalculate relevant damage, accuracy and speed descriptions as state changes. A Pokémon knocked out by the first action does not act. A newly inflicted status can affect the second action. There is no general end-of-turn residual-damage phase.

5

Merge equivalent outcomes, then recurse.

If separate damage rolls or order paths end with identical modeled HP, status, counters, stages and PP, combine their probability. Continue from that state into another whole turn, unless it is terminal, cached, unsupported, or limited by the search budget.

“A narrow winning path” has a precise meaning.

Suppose a move has a 90% hit chance and always wins on a hit. If missing leaves a continuation with a 40% win chance, that move pair is worth 0.9 × 1 + 0.1 × 0.4 = 94%. If missing instead guarantees defeat, it is 90%. This is a hypothetical example of probability propagation. Being far ahead does not eliminate every random loss path—but incomplete search must not be confused with an actual loss path.

Implemented in analysis/outlook.mjs → simulateOutlook; damage and move descriptions come from analysis/threat.mjs → analyzeBattle and the bundled Run & Bun calculator.

03 / Interpretation

A lower bound is not the win rate.

Current display behavior (October 9): The solid bars and numbers smoothly follow a provisional midpoint of the current search bounds, with roughly quarter-second search passes. The midpoint is a display estimate, not a calibrated probability. The API still exposes the actual lower and upper bounds. A completely unknown interval does not invent a new score. Stripes and range labels are no longer displayed.

A completed search can establish a narrow outcome interval. An unfinished search may establish only a floor and a ceiling. [50%, 100%] means the modeled value is somewhere between 50% and 100%. It does not establish that losing has a 50% chance. Loss probability, within this model, could be anywhere between 0% and 50%.

What I actually observed in the live API

During this guide’s audit, one response reported lower bound 50%, upper bound approximately 100%, and displayed score 60%. It reported complete: false, budget_exhausted: true, root_reused: true, and 4,269 new decision-state expansions. The attempted depth was 128.

The 60% was a retained display estimate within the bounds. It was neither a newly solved 60% win rate nor evidence of a 40% loss chance. This is one observed response, not a recording of your reported swings.

04 / Continuity

What “move down the tree” currently means.

The running worker keeps a table of previously searched states. After an observed turn, the new state becomes the root. If the same state was already reached in the search, its saved bounds can be used immediately. A solved descendant can need zero new expansions.

State identity includes both battlers’ HP, status, sleep and confusion counters, seven stat stages, and each selected move’s PP. Reuse is valid only under the same model context: species, move sets, level/build, items, abilities, field, restrictions and exact stats. Context changes discard the table; leaving battle or a non-battle tracking status also cancels the worker.

What is retained

Up to 40,000 state-bound entries and 80,000 depth-cache entries, kept in one worker. Within a compatible context, different histories that lead to the same modeled state can share results.

What is still rebuilt

Move descriptions, damage caches and transitions are constructed again for each scoring call. An unresolved state is expanded again while consulting saved bounds. There is no retained frontier that resumes at exactly the next unfinished edge.

Therefore, the current implementation is persistent state-value reuse. It is not yet a complete tree controller that follows each observed action, resolves partial turns, and schedules only the most important unresolved continuations.

Search order and actual work limits
  • Try a zero-time warm lookup when saved states exist. Return a matching root’s bounds immediately.
  • Run a 150 ms pass followed by repeated 250 ms passes. There is no total time or pass-count limit. Publish every pass; stop when the modeled interval is within 0.2 percentage points or the observed battle state changes.
  • Attempted depth begins at 128 whole turns and increases by 32 per pass. Decision-state expansion counts have no separate cap. These time budgets are checked during traversal rather than enforced as hard wall-clock deadlines.
  • Chance branches are visited in descending immediate probability. Merge equal successor states, reuse valid state certificates, and prune provably dominated actions. Repeated states on the current recursion path use existing bounds; later passes refine cycles using their exit branches.
  • Multi-action matrices start with 256 fictitious-play iterations; the allowance increases by 256 each pass. Cancellation and time checks also apply during matrix refinement.
  • The search supports an optional path-probability cutoff, but the live worker does not enable it. The chance-tail cutoff is 10−12, with discarded probability retained as uncertainty.
  • Depth-specific memo entries are capped at 80,000. State certificates remain until the matchup changes or battle ends; memory can grow with explored states.
  • Unsupported mechanics remain unknown. Continuous computation cannot guarantee a solution for an incomplete transition model.

Implemented in analysis/search.mjs, run-bun/search-worker.mjs and run-bun/search-service.mjs.

05 / Failure modes

Why the number can still swing after an attack.

Tree reuse solves only part of the problem. The system still has to know which real state to evaluate, model its consequences correctly, and present its uncertainty honestly.

The invariant we should demand

If the original state is an exact 100% modeled win, and the actual optimal action leads to a supported, nonzero-probability descendant in that same model, the descendant must also be a win. It should not drop to 48% simply because a predictable sleep counter expired.

If it does, that is evidence to investigate state alignment, mechanics, cache identity or publication—not a reason to defend the fluctuation as normal. The existing deterministic wake-up tests check this invariant, but do not verify real emulator turn alignment.

The native overlay polls every 800 ms and eases to a new target over 450 ms. That is cosmetic animation. It cannot fix an incorrect target or restore a result cleared by the tracking pipeline.

06 / Model fidelity

What the future simulation actually carries forward.

AreaCurrent behavior
HP, PP, move orderAdvance within the tree. Damage rolls, priority, speed, Trick Room and equal-speed order branches are modeled. PP exhaustion blocks a move; Struggle is not modeled.
SleepKnown counters decrement before an action; Early Bird decrements by two. Waking permits an action. Unknown counters lead to unresolved continuations. Newly inflicted sleep uses equal-weight counters 2, 3 and 4: a provisional duration model, not verified for this ROM.
Freeze, paralysis, confusionOrdinary thaw branches use 20%; supported self-thaw moves thaw immediately. Paralysis prevents an action with probability 25%. Confusion counters advance; a surviving counter branches to self-hit with probability 1/3. Self-hit uses maximum computed base damage, not randomized rolls.
Accuracy and evasionMove accuracy comes from the bundled move table. Relative stages are clamped to −6…+6; multiplier is (3 + stage)/3 for nonnegative stages and 3/(3 − stage) otherwise. Accuracy is floored and clamped to 1…100%. Listed always-hit moves bypass this. Missing/non-numeric accuracy assumes a hit. Ability, item and weather accuracy modifiers are absent.
Setup, stat drops, recovery, statusA specific allowlist: Swords Dance, Nasty Plot, Calm Mind, Dragon Dance, Agility, Iron Defense; Growl, Leer, Tail Whip, Sand Attack, Smokescreen; Recover, Slack Off, Soft-Boiled, Milk Drink; Sing, Hypnosis, Sleep Powder, Spore, Thunder Wave, Will-O-Wisp, Poison Powder. Selected immunities are checked. This is not general move-script simulation.
Fields and restrictionsCurrent field effects feed damage/order calculations. Taunt, Disable, Encore and move locks restrict current legal choices. Their expiration is not evolved; weather, terrain, screens and Tailwind are not generally timed out.
Poison and burnStatus can be carried or inflicted; supported damage modifiers can apply through the calculator. There is no general poison/burn residual HP loss at turn end.
Other move effectsNo general recoil/drain, secondary flinch or status, reactive move handling, or multi-turn move engine. Calculator damage support does not mean the move’s full consequences are simulated.
Abilities and itemsThe community calculator supplies many immediate damage interactions. This does not supply a general event system for all reactive triggers or future state changes.
Critical hits and teamsNo stochastic critical-hit branches; a current build flag can request critical damage. No reserve teams, switching, trainer progression or full-battle endpoint. Double battles are rejected.

Searching an inaccurate transition model more deeply does not make it accurate. Extra computation can narrow the interval around the wrong game. Mechanics fidelity and search completeness are separate requirements.

07 / Development direction

What needs to change for the intended predictor.

These are proposed priorities, not features implemented by this guide.

  1. Align observations with real battle phases. Verify a Run & Bun turn marker. Distinguish move selection, first action, second action, end-of-turn effects and switching. Update the search from an observation that describes where the game actually is.
  2. Define the probability’s target. Full-trainer-battle victory with the remaining team, under an explicit player policy and a verified ROM AI model. Keep an adversarial matchup value as a separate diagnostic if useful.
  3. Use a persistent search graph with an explicit frontier. Retain successor edges and probability mass, condition on the observed outcome, discard incompatible futures, and prioritize unresolved states by their potential impact on the root interval. Add move ordering and suitable bound pruning; do not spend the budget diving down arbitrary listed moves.
  4. Implement a faithful event-based transition engine. Evolve counters, residual damage, triggers and switches in the correct order. Validate one mechanic at a time against controlled emulator behavior.
  5. Make uncertainty visible without faking a loss chance. Distinguish solved stochastic risk, unresolved work, unsupported mechanics and held display values. A scalar estimate needs a defined estimation method; using a lower bound or clamping the old value is not that method.
  6. Trace every large movement of the meter. Record phase, observation identity, model-context changes, cache reuse, chosen actions, interval endpoints and display provenance. A regression should replay the actual failure before a repair is called verified.

More CPU helps when the model and state are right but the interval is broad. It will not correct a mid-turn root, a missing team, an incorrect enemy policy or an omitted mechanic. The current architecture uses one search worker; throwing more cores at it does not automatically parallelize the work.
